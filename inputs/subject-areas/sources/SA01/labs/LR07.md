# LR07 Применение программной избыточности и оценка её стоимости

SA01 Электронное расписание

Вы готовите решение для системы «Электронное расписание» (OKFKS-SA01). Её критичная функция — публикация и просмотр актуального расписания. Для освоения метода ниже используется отдельный учебный эпизод. Сервис CHECK-API проверяет корректность учебных идентификаторов. Базовая реализация не достигает требования успешности. Команда рассматривает повтор запроса, резервный кэш и запасного поставщика. Нужно сравнить варианты программной избыточности по эффекту, стоимости и ограничениям, не создавая реальную внешнюю инфраструктуру. Перенос на вашу предметную область выполняется последним действием: необходимо объяснить последствие для конкретного актива, а не только заменить название системы.

Избыточность оценивается по реально спасённым операциям и цене. Повтор безопасен только при контроле повторного побочного эффекта; общий источник сбоя может сделать резерв бесполезным.

Используйте признаки переключения и сохранения состояния из ЛР06. Проверяйте допущения каждой модели избыточности отдельно.

В ЛР08 передайте события включения резервного пути и счётчик восстановленных операций. В ЛР10 используйте стоимость, ограничение и остаточный риск выбранной меры.

## Паспорт применения к выбранному варианту

Система: Электронное расписание (OKFKS-SA01).

Критичная функция: публикация и просмотр актуального расписания.

Активы: расписание, учётные записи, журналы.

В отчёте сохраняйте один вариант SA01–SA30 на весь курс. Если исходные эпизоды имеют разные имена узлов или окна наблюдения, переносите метод и структуру доказательств, а не объединяйте их числовые итоги.

## Базовые значения

Requests Per Cycle: 100000

Success Rate: 0.992

Transient Failure Rate: 0.006

Persistent Failure Rate: 0.002

Требование: модельная доля успешных запросов не ниже 0.997

Added Cost Limit Rub: 18000

Calculation Period: первый расчётный цикл после внедрения

## Принятые допущения

Доли отказов заданы относительно всех запросов и не пересекаются.

Спасённый запрос добавляется к базовой доле успеха; результат не может превышать 1.

Эффекты разных вариантов не складываются автоматически: комбинацию нужно моделировать отдельно.

Стоимость первого цикла = внедрение + эксплуатация за цикл.

## Подсказки к расчёту

Для A добавка к успеху = transientFailureRate × 0.95.

Для B добавка = общая доля отказов × 0.60 × 0.98.

Для C добавка = общая доля отказов × 0.96.

Сравнивайте не только вероятность, но и стоимость первого цикла и ограничения.

## Actions

Заполните сравнительную таблицу A–D и покажите формулу для каждого модельного эффекта.

Проверьте требование успешности и бюджет первого цикла отдельно.

Для каждого варианта укажите преимущество и техническое ограничение из условий системы.

Выберите один вариант или обоснованную комбинацию, не превышающую бюджет; для комбинации явно исключите двойной учёт спасённых запросов.

Постройте схему «основной путь — обнаружение сбоя — избыточный путь — фиксация результата».

Сделайте итоговое решение и назовите остаточный риск.

Укажите, имеет ли повтор критичной операции вашего варианта побочный эффект; предложите признак дубликата и проверку отсутствия повторной записи в выбранный актив.
